## 5. Reminder engine and scheduler

- [x] 5.1 Declare `IReminderService.GenerateDueAsync(CancellationToken)` and implement `ReminderService` (design D3, D4, D5, D7). It returns immediately when reminders are disabled. It loads candidate tasks within the deadline window, resolves the active and de-duplicated recipients (task_recipients ∪ creator), and for each due reminder and recipient runs insert-or-ignore on `reminder_history` followed by a `Notification` (DeadlineReminder or Overdue, linked to the task, with a message naming the title and when it is due) in one transaction. Register it in `Program.cs`. Verify with unit tests using a fake `TimeProvider`: assignee, creator and additional recipient each get exactly one notification; a creator who is also a recipient gets one; an inactive recipient is skipped; the global switch off yields nothing; and the history row has status Sent, ProcessedAt and the slot.
- [x] 5.2 Add idempotency tests against a real SQLite file: run `GenerateDueAsync` several times at the same instant, and twice from separate scopes, and assert one history row and one notification per recipient. Move the clock to the next day and assert the next reminder appears. Mark the task Completed and assert nothing more is generated. Change the deadline and assert reminders follow the new date. Verify `dotnet test` passes.
- [x] 5.3 Add `ReminderEngineOptions` and a `ReminderSchedulerService : BackgroundService` that runs one pass at startup and then one per `PeriodicTimer` tick. Each pass runs in its own DI scope and logs exceptions without stopping the loop. Register it only when `Reminders:SchedulerEnabled` is true, and set it to false in `TaskFlowApiFactory`. Verify that the integration suite still passes, and manually confirm in `dotnet run` logs that a pass runs at startup and every minute.
