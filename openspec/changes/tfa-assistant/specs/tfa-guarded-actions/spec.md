# Spec Delta

## Purpose

Lets TFA act on the user's behalf (drafting and sending mail, and routing password, profile and
role-change requests) only through the application's own authorization, only for the signed-in user,
and only after the user explicitly confirms.

## ADDED Requirements

### Requirement: Backend authorization for every action

Before preparing or performing any action, the system SHALL check, in the backend, that the signed-in
user is allowed to perform it, using the same authorization rules as the application's own screens
and API. The check SHALL apply to every request, typed or spoken, and SHALL NOT depend on what the AI
model says.

#### Scenario: Same rules as the screens

- **WHEN** an Employee asks TFA to do something that the application refuses an Employee
- **THEN** TFA refuses it and nothing is changed

#### Scenario: Model output cannot grant permission

- **WHEN** the model's reply claims the user is allowed to perform an action the user's role does not permit
- **THEN** the backend still refuses the action

#### Scenario: Voice and chat are equal

- **WHEN** the same request is made by voice and by typing
- **THEN** both receive the same authorization outcome

### Requirement: TFA has no privileges of its own

TFA SHALL act only with the signed-in user's identity and permissions, and SHALL NOT offer or
prepare any action that the application would refuse that user.

#### Scenario: Action not offered

- **WHEN** an Employee asks what TFA can do
- **THEN** TFA lists only actions that an Employee is permitted to perform

### Requirement: Refusals are explicit and fixed

When an action is not permitted, TFA SHALL say so in a fixed message that is not generated by the
model. The message SHALL state that the user does not have the required permission, what the action
is, which role or party can perform it, and what to do next. It SHALL NOT perform the action in part
or offer a workaround that bypasses the rules.

#### Scenario: Employee asks for the Manager role

- **WHEN** an Employee asks TFA to change their role from Employee to Manager
- **THEN** TFA replies that they do not have the required permission, that changing a role can only be performed by an authorized administrator, and asks them to contact their system administrator; no role is changed

#### Scenario: Manager asks for the Administrator role

- **WHEN** a Manager asks TFA to make them an Administrator
- **THEN** TFA refuses with the same explanation and no role is changed

#### Scenario: Administrator-only request

- **WHEN** a non-administrator asks TFA to deactivate a user or change application settings
- **THEN** TFA explains that this needs an administrator and no change is made

### Requirement: Explicit confirmation for state-changing actions

Any action that changes data or sends something SHALL first be shown to the user as a pending action
with its full details, and SHALL only be performed after the user confirms it through a separate
confirmation request. The AI model SHALL NOT be able to confirm an action. A pending action SHALL
belong to the user who requested it, SHALL expire after a short time, and SHALL be performed at most
once. The user SHALL be able to cancel it or ask for changes.

#### Scenario: Pending until confirmed

- **WHEN** TFA prepares an action
- **THEN** nothing has changed or been sent until the user clicks Confirm

#### Scenario: Confirmation by another user

- **WHEN** a user tries to confirm a pending action that belongs to someone else
- **THEN** it is reported as not found and nothing is performed

#### Scenario: Expired action

- **WHEN** a user confirms a pending action after it has expired
- **THEN** it is refused with a message to ask TFA again and nothing is performed

#### Scenario: Confirmed twice

- **WHEN** a user confirms the same pending action a second time
- **THEN** the action is not performed again

#### Scenario: Permissions rechecked at confirmation

- **WHEN** a user's role changes between preparing and confirming an action so that it is no longer permitted
- **THEN** the confirmation is refused and nothing is performed

### Requirement: Email drafting and review

When the user asks TFA to write an email, TFA SHALL prepare a draft with recipients, subject and body
based on the user's request and, when a task is named, the task's details. The draft SHALL be shown in
full for review. The user SHALL be able to edit the recipients, subject and body, or cancel, before
sending. Recipients SHALL be TaskFlow users, because mail is internal.

#### Scenario: Draft shown for review

- **WHEN** a user asks TFA to send a mail to their manager about a task
- **THEN** TFA shows the recipient, subject and body in a review card with Send, Edit and Cancel

#### Scenario: Editing before sending

- **WHEN** the user edits the subject in the review card and confirms
- **THEN** the mail is sent with the edited subject

#### Scenario: Unknown recipient

- **WHEN** the requested recipient is not an active TaskFlow user
- **THEN** TFA says it could not find that person and does not prepare a sendable mail

### Requirement: Manager resolution

When the user asks for mail to "my manager" about a task, TFA SHALL address it to the task's creator
when that is a different active user, and otherwise to the active Manager in the sender's department when there is exactly one.
When neither can be found, or the department has more than one Manager, TFA SHALL ask the user to choose a recipient.

#### Scenario: Task creator is the manager

- **WHEN** an Employee asks to mail their manager about a task created by an active Manager
- **THEN** the draft is addressed to that Manager

#### Scenario: Creator is the sender

- **WHEN** the user created the task and has a department with an active Manager
- **THEN** the draft is addressed to the department's Manager

#### Scenario: Several managers in the department

- **WHEN** the task was created by the sender and the sender's department has two active Managers
- **THEN** TFA asks the user which Manager to address

#### Scenario: No manager found

- **WHEN** neither a different creator nor a department Manager exists
- **THEN** TFA asks the user whom to address

### Requirement: Mail is sent as the user through Mail

Confirming an email SHALL send it through the application's internal mail as the signed-in user, so
it appears in the user's Sent folder and the recipients' Inboxes, and the user's mail permissions
apply. TFA SHALL report the result, including a failure, and SHALL not report success unless the mail
was sent.

#### Scenario: Confirmed mail is sent

- **WHEN** the user confirms a reviewed draft
- **THEN** the mail appears in the user's Sent folder and in each recipient's Inbox, and TFA says it was sent

#### Scenario: Send fails

- **WHEN** sending fails after confirmation
- **THEN** TFA says the mail was not sent and why, and the pending action cannot be mistaken for a sent mail

### Requirement: Own profile updates

When a user asks TFA to change their own name or email, TFA SHALL treat it as a pending action limited
to the fields a user may change on their own profile, show the change for confirmation, and apply it
through the same rules as the Profile screen. TFA SHALL NOT change any other profile field, including
role, department or active status.

#### Scenario: Change own name

- **WHEN** a user asks TFA to change their name to "Asha Nair" and confirms
- **THEN** their name is updated and TFA confirms it

#### Scenario: Change of another user

- **WHEN** a user asks TFA to change another user's name
- **THEN** TFA explains that only that user, or an administrator through the Employees screen, can do so, and nothing is changed

### Requirement: Password changes stay in the Profile screen

TFA SHALL NOT collect, receive, store or transmit passwords. When a user asks to change their
password, TFA SHALL explain the steps and link to the password-change form on the Profile screen,
where the user's own authorized process applies. A request to change another person's password SHALL
be refused with the administrator guidance.

#### Scenario: Own password

- **WHEN** a user asks "change my password"
- **THEN** TFA explains the steps and links to the Profile screen and asks for no password

#### Scenario: Someone else's password

- **WHEN** a user asks TFA to change a colleague's password
- **THEN** TFA refuses, explains that this needs an administrator, and makes no change

### Requirement: Role changes are never made for non-administrators

TFA SHALL NOT change any user's role at the request of a non-administrator, including their own.
For an Administrator, a role change SHALL be a pending action that is shown for confirmation and
performed through the same rules as the Employees screen, changing only the role and leaving every
other field of that user as it was. The affected user's sessions end, as they do on the Employees
screen.

#### Scenario: Administrator changes a role

- **WHEN** an Administrator asks TFA to make an Employee a Manager and confirms
- **THEN** that user's role becomes Manager through the same rules as the Employees screen

#### Scenario: Other fields untouched

- **WHEN** an Administrator confirms a role change for a user
- **THEN** that user's name, email, department and active status are unchanged

#### Scenario: Application rule refuses the change

- **WHEN** the application's own rules reject the role change after confirmation
- **THEN** TFA reports the refusal and the role is unchanged

### Requirement: Actions are recorded

The system SHALL record each prepared, confirmed, cancelled, expired and refused action with the user,
the kind of action, the outcome and the time, without storing message bodies, passwords or keys in
the record.

#### Scenario: Refusal recorded

- **WHEN** an Employee's role-change request is refused
- **THEN** an audit record exists with the user, the action kind and the outcome "refused"

#### Scenario: No secrets in the record

- **WHEN** a mail action is recorded
- **THEN** the record holds the kind and outcome and not the mail body
