## 1. Overview
TFA Settings is the screen where an authorized user chooses the AI model behind TFA, the TaskFlow Assistant. Three providers are built in – a free local server (Ollama) and two cloud services (Google Gemini, OpenAI GPT) – and an administrator can add **custom providers**: any service that uses the OpenAI-compatible or Ollama API (for example Groq, Mistral, OpenRouter, or a company server running LM Studio or vLLM), added by typing a new provider name. The screen is a read-only list of every model: **Use this model** switches TFA to a model in one click, **Test connection** checks any model, and models an administrator added can be edited, moved to another provider or deleted. Provider names, model names, API keys and server addresses are typed only on the Add AI model screen and its edit mode. API keys are stored encrypted, one per provider.

## 2. Purpose / Business Value
- The organization chooses which AI provider TFA uses: a free local server (Ollama), a cloud service (Google Gemini, OpenAI GPT), or a custom provider of its own choice.
- A new OpenAI-compatible or Ollama service can be connected just by typing its name and address; nothing has to be built into TaskFlow for it.
- API keys are stored encrypted and are never shown again or sent back to the browser.
- A one-click connection test on any listed model confirms it works before users rely on it.
- One list shows every model, which one TFA uses, and whether its provider has a key, so it is clear which settings belong to which model.
- Only one model is offered to users in the TFA window, so everyone uses the configuration the administrator chose.

## 5. Screen & Functionality Details

### 5.1 Screen: TFA Settings
**Purpose:** See every AI model TFA can use, switch TFA to one with a click, test any of them, and add, edit or delete the models an administrator added. Keys and addresses are typed only on the Add AI model screen (5.2) and its edit mode.
**Who can see this screen:** Administrator (and custom roles granted `settings.ai.view`).
**Required permission:** `settings.ai.view` (to open). `settings.ai.edit`, `settings.ai.test` and `settings.ai.model.remove` for the actions.

**Screen Elements**
- Page title **TFA settings**, and an **AI models** section that explains the choices. **Use this model** switches TFA to a model; a model is added, or one you added is changed, on the Add AI model screen. Ollama runs on your own server and is free. Google Gemini has a free tier with limits. OpenAI GPT has no free tier. Gemini and OpenAI are cloud services, so a user's question and related task details are sent to them. A custom provider marked **Cloud** is treated the same way; one marked **Local** is treated like Ollama.
- **Add AI model** button next to the **AI models** heading (shown only with both `settings.ai.edit` and `settings.ai.test`). It opens the Add AI model screen (5.2).
- A line such as "TFA uses **llama3.2:3b** on **Ollama**." (or "TFA has no model in use yet. Choose **Use this model** on a model below.").
- A read-only list of every model, grouped by provider: first **Ollama**, **Google Gemini**, **OpenAI GPT**, then each custom provider by name, each with its **Local** / **Cloud** tag. Each row shows:
  - the model ID, for example `gemini-3.8-flash`;
  - "{Provider} · Local" or "{Provider} · Cloud";
  - the key status – "Key saved, ends …1234", "No key saved" or "The saved key can no longer be read" – or, for Ollama, its server address. A custom provider shows its server address, followed by " · key ends …1234" when a key is saved. The key belongs to the provider, so every row of that provider shows the same status;
  - **Built-in** or **Added by you** (every model of a custom provider is **Added by you**);
  - an **In use** badge on the one model TFA uses.
- Actions on each row:
  - **Use this model** (with `settings.ai.edit`; not on the row in use). It is disabled, with the hint "No key saved for {Provider} yet. Add it on the Add AI model screen.", when a cloud provider has no key that can be read.
  - **Test connection** (with `settings.ai.test`). The result appears on that row.
  - **Edit** (with `settings.ai.edit` and `settings.ai.test`) and **Delete** (with `settings.ai.model.remove`), only on models an administrator added. Built-in models cannot be edited or deleted.
- On a phone, each row is shown as a stacked card with the same details and buttons, without scrolling sideways.
- There is no Model or Server dropdown, no API key or server address box, no **Remove this model from the list** and no **Save TFA settings** button any more (removed in v1.3).

### 5.2 Screen: Add AI model
**Purpose:** Add a model that is not in the list yet, and prove it works before anything is saved.
**Who can see this screen:** Administrator (and custom roles granted both `settings.ai.edit` and `settings.ai.test`).
**Required permission:** `settings.ai.edit` and `settings.ai.test`. A user without `settings.ai.test` who opens the address is sent back to TFA Settings.

**Screen Elements**
- **Back to TFA settings** link at the top, and a **Cancel** link next to the button. Both return to TFA Settings and save nothing.
- **AI provider** * (required, asked first): a text box, not a dropdown. While typing it suggests the existing providers – Google Gemini, OpenAI GPT, Ollama and any custom providers, each with Local or Cloud. A name that matches an existing provider (in any case, for example "google gemini") is that provider. The other fields appear once a provider is typed. Left empty, the screen says "Enter the AI provider."
- New provider (a name that matches no provider): a **New provider** tag next to the label and the hint "A provider TaskFlow does not know yet. It is added when the test works. Most services (Groq, Mistral, OpenRouter, LM Studio, vLLM) use the OpenAI-compatible API." The screen then asks for:
  - **API type** * – **OpenAI-compatible** or **Ollama**;
  - **Runs** * – **Cloud** (questions leave the organisation; the default) or **Local** (on your own server);
  - **Server address** * – the address the service gives for its API, including the version path, for example `https://api.groq.com/openai/v1` (empty: "Enter the server address.");
  - **API key** (optional, OpenAI-compatible only) – "A local server may need no key. The key is stored encrypted and never shown again."
  The provider name must be 2 to 40 characters and not already used by another provider (in any case).
- **Model name** * (required, 1–100 characters, no spaces). It is the provider's model ID; the box shows an example for the provider's API type: `gemini-3.8-flash` (Google Gemini), `gpt-4o-mini` (OpenAI GPT and OpenAI-compatible), `llama3.2:3b` (Ollama). For a custom provider any ID without spaces is accepted, for example `meta-llama/Llama-3.3-70B-Instruct`.
- Gemini / OpenAI: **API key**. It is required (*) when the provider has no saved key. When a readable key is saved, the box may be left empty to keep it, and the hint says "A key is saved (ends …1234). Leave the box empty to keep it. A new key replaces it for every {Provider} model."
- Google Gemini only: a hint "Create a Gemini key in Google AI Studio" with a link to https://aistudio.google.com/apikey. The screen does not judge a key by how it starts (current AI Studio keys start with `AQ.`, older ones with `AIza`; both work).
- Ollama: **Server address** (optional). Left empty, the saved address or `http://localhost:11434` is used.
- An existing custom provider: **Server address** (optional, empty keeps the saved one) and, for OpenAI-compatible, **API key** (optional).
- **Test connection** button ("Testing…" while it runs) and, after a failure, the reason followed by "Nothing was saved."

**Edit mode – Edit AI model** (opened by **Edit** on a model an administrator added; address `/settings/tfa/models/{providerId}/{model}/edit`; same permissions as Add AI model)
- Title **Edit AI model**: "Change the model name, enter a new key or server address, or type another provider to move the model there, and test the connection. The changes are saved only when the test works; the model TFA uses does not change."
- **AI provider** is filled in with the model's provider and can be changed (until v1.3 it was fixed). Typing another existing provider, or a new name (with the new-provider fields above), shows "The model moves to {target} when the test works."
- **Model name** is filled in with the current name.
- Gemini / OpenAI / custom OpenAI-compatible: **API key** box, empty. The hint says "A key is saved (ends …1234). Leave the box empty to keep it. A new key replaces it for every {Provider} model."
- A provider with a saved key: **Remove the key** button (hidden while the provider is being changed).
- Ollama or a custom provider: **Server address** (optional).
- **Test and save** button ("Testing…" while it runs), **Back to TFA settings** and **Cancel**.
- Opening the edit address of a model that is not listed, is built in, or is the one TFA uses returns to TFA Settings with the reason.

### 5.4 Step-by-Step Workflow – Choose the Model TFA Uses
1. User opens **Settings → TFA Settings**.
2. System lists every model, grouped by provider, and marks the one TFA uses now with **In use**.
3. User finds the model to use. To use a model that is not listed, the user adds it on the Add AI model screen instead (5.5).
4. User clicks **Use this model** on that row.
5. System checks that the model is listed and, for Gemini or OpenAI, that a key is saved and can be read.
6. System switches that provider on with this model. The others are switched off, but their keys and models stay stored. The toast *"{model} on {Provider} is now in use"* is shown and the list is refreshed.
7. From now on, only this model is offered in the TFA window.

**Flow Diagram**
```mermaid
flowchart LR
  A["Open TFA Settings"] --> B["Find the model in the list"]
  B --> C["Click Use this model"]
  C --> D{"Key saved for a cloud provider?"}
  D -- No --> F["Button disabled: No key saved for Provider yet"]
  D -- Yes --> G["Switch this provider on, others off"]
  G --> H["Toast: model on Provider is now in use"]
```

### 5.5 Step-by-Step Workflow – Add an AI Model
1. On TFA Settings, the user clicks **Add AI model**. The Add AI model screen opens.
2. User types the **AI provider**, or picks it from the suggestions. A new name adds a custom provider (5.11).
3. User types the **Model name**.
4. For Gemini or OpenAI, the user pastes the **API key** (it may be left empty when a key is already saved). For Ollama or a custom provider, the user may type the **Server address**.
5. User clicks **Test connection**. The screen checks the required fields first and sends nothing if one is missing.
6. The system sends one short request ("Reply with OK.") to the provider with the typed values. **Nothing is saved before this test works.**
7. If the test fails, the reason is shown with "Nothing was saved.", the key box is emptied, and the other values are kept so the user can correct them.
8. If the test works, the system, in one step, adds the model to the list (if it is new), saves the key (or Ollama address) for that provider, switches that provider on with this model, and switches the others off (their keys and models stay stored).
9. The toast *"{model} on {Provider} is now in use"* is shown and the user is returned to TFA Settings, which shows the new model as the one TFA uses.
10. **Back to TFA settings** or **Cancel** at any time returns to TFA Settings without saving.

**Flow Diagram**
```mermaid

  A["TFA Settings: click Add AI model"] --> B["Type or pick the AI provider"]
  B --> C["Enter model name and API key or address"]
  C --> D["Click Test connection"]

  E -- No --> F["Show field error"] --> C
  E -- Yes --> G["Test with the typed values"]
  G --> H{"Test works?"}
```

### 5.6 Step-by-Step Workflow – Test Connection
1. User clicks **Test connection** on a model's row ("Testing…" while it runs).
2. System sends one short request ("Reply with OK.") to that row's provider, with that row's model and the saved key or address. This also works for a provider TFA does not use right now. Nothing is saved, and the model TFA uses does not change.
3. The result appears on that row: *"The connection works."* or a plain message explaining the problem (for example the key was not accepted, Ollama is not running, or *"No key saved for {Provider} yet. Add it on the Add AI model screen."*).
4. When the model is not available, or the provider gave an error TaskFlow does not recognise, the message also shows the provider's own reason, for example *"Google Gemini said: HTTP 404 - …"* (at most 200 characters; anything that looks like an API key is replaced by `[key]`). Google, for example, names the model to use instead of a retired one. The reason is shown only by **Test connection** here and on the Add AI model screen, which need `settings.ai.test`; TFA users in the chat see only the plain message.

**Flow Diagram**
```mermaid
flowchart LR
  A["Click Test connection on a row"] --> B["Send test request with that model and the saved key or address"]
  B --> E{"Provider answered?"}
  E -- Yes --> F["The connection works."]
  E -- No --> G["Show failure message on the row"]
```

### 5.7 Step-by-Step Workflow – Delete a Model
1. User clicks **Delete** on the row of a model they added. Built-in models have no **Delete**.
2. If TFA uses this model, a message says *"{model} is in use by TFA. Switch TFA to another model first, then delete it."* with only an **OK** button, and nothing changes.
3. Otherwise the system asks *"Delete {model}?"* ("{model} is removed from the {Provider} models. The {Provider} key stays saved."). **Cancel** removes nothing.
4. After **Delete**, the system removes the model and refreshes the list. If a provider that is switched off still had this model saved, its model goes back to the provider's default (for example `gemini-3.8-flash`). If it was the last model of a custom provider, the custom provider and its key are removed too and its group disappears; a built-in provider is never removed. The toast *"Deleted {model}"* is shown.

### 5.8 Business Rules & Validations
- Three providers are built in: **Ollama** (local, no key), **Google Gemini** and **OpenAI GPT** (cloud, need a key). Any number of **custom providers** can be added; each uses the **OpenAI-compatible** or **Ollama** API (not the Google Gemini API), has a name of 2 to 40 characters that no other provider uses (in any case), a server address, **Local** or **Cloud** (default Cloud), and an optional key. A provider cannot be renamed or change its API type later.
- A custom provider is created only when the connection test of its first model works. When its last model is deleted or moved away, it is removed with its key. Built-in providers are never removed.
- A typed provider name that matches an existing provider in any case is that provider; any other name is a new provider. "gemini" is not "Google Gemini", so it would be a new provider – the **New provider** tag shows this.
- On Edit, changing the provider moves the model there only when the test on that provider works. A name that provider already lists is refused ("That model is already in the list."), the model TFA uses cannot be moved, and **Remove the key** cannot be combined with a move. Moving never changes which model TFA uses.
- Upgrading from an earlier version keeps everything: Google Gemini, OpenAI GPT and Ollama become the built-in providers with their keys, models, saved model and on/off state, and earlier TFA messages still show which provider answered.
- Document search always uses the built-in Ollama provider; a custom Ollama provider is used for chat only.
- Built-in models: Ollama `llama3.2:3b`, `llama3.2:1b`, `llama3.1:8b`, `qwen2.5:7b`, `mistral:7b`. Gemini `gemini-3.8-flash`, `gemini-3.5-flash`, `gemini-3.5-flash-lite`. OpenAI `gpt-4o-mini`, `gpt-4o`, `gpt-4.1-mini`. The first one is each provider's default.
- Settings saved earlier that still name a Gemini model Google no longer offers to new keys keep that name. **Test connection** then reports that the model is not available (with Google's reason), and the administrator clicks **Use this model** on a current model.
- TFA Settings itself is read-only. Model names, keys and addresses are typed only on the Add AI model screen and its edit mode, and are saved only after the connection test works. Removing a key needs no test.
- On a brand-new installation, Ollama is switched on at `http://localhost:11434`. The cloud providers start switched off and without a key. On an upgraded installation, TFA stays off until an administrator turns it on.
- The model name must be 1–100 characters and contain no spaces: it is the provider's model ID (for example `gemini-3.8-flash`), not a display name. This is checked on the Add AI model screen and its edit mode. Google Gemini IDs also follow Gemini's lowercase format; OpenAI-compatible and Ollama providers accept any ID without spaces.
- On the Add AI model screen, the provider and the model name are required. An API key is required for Gemini and OpenAI only when no readable key is saved. A server address is required only for a new custom provider.
- A model is added only after its connection test works. A failed test saves nothing: not the model, not the key, and not the provider choice.
- API keys are kept one per provider. A key entered on the Add AI model screen or its edit mode replaces that provider's saved key for all of its models, so every row of that provider shows the same key status.
- **Use this model** needs a readable key for Gemini and OpenAI. Without one it is disabled with "No key saved for {Provider} yet. Add it on the Add AI model screen.", and the server refuses it too.
- "In use" means the model saved on the provider that is switched on. Only that one model is marked **In use**.
- Editing a model saves only after its test works, renames it if the name changed, and never changes which model TFA uses. A new name that is already listed is refused.
- Adding a model that is already in the list does not add it twice; it becomes the model in use.
- Every server address (Ollama or a custom provider) must be a valid http or https URL, at most 300 characters. Cloud metadata and link-local addresses (for example 169.254.x.x, `metadata.google.internal`) are refused. `localhost` and private addresses are allowed.
- The API key can be at most 500 characters and cannot contain spaces. Ollama (built-in or custom) does not use a key. A custom provider's key is sent to it only when one is saved.
- A key is write-only. After saving, only "key set" and its last four characters are shown. Leaving the key box empty keeps the saved key.
- You cannot send a new key and ask to remove the key in the same request. **Remove the key** is done on its own, without other changes.
- Built-in models are read-only: they have no **Edit** or **Delete**, and a request to change or remove one is refused.
- The model TFA uses cannot be edited or deleted. Switch TFA to another model first. A model saved only for a provider that is switched off can be edited (its saved name follows) or deleted (its saved model goes back to the provider's default).
- A provider counts as **configured** when it is switched on, has a model, and has either an address (Ollama, custom provider) or a key that can still be decrypted (Google Gemini, OpenAI GPT).
- If the saved key can no longer be decrypted (for example the server's key ring was lost), the screen says *"The saved key can no longer be read. Enter it again."*

### 5.10 Step-by-Step Workflow – Edit an Added Model
1. On TFA Settings, the user clicks **Edit** on the row of a model they added. If TFA uses this model, a message says *"{model} is in use by TFA. Switch TFA to another model first, then edit it."* with only an **OK** button, and the edit screen does not open.
2. The **Edit AI model** screen opens with the provider and the model name filled in; both can be changed (5.2, edit mode).
3. The user changes the **Model name**, and/or pastes a new **API key** (Gemini, OpenAI, custom OpenAI-compatible) or types a **Server address** (Ollama, custom provider). An empty key box keeps the saved key. A new key replaces the key for every model of that provider. To move the model, the user types another provider – an existing one, or a new name with the new-provider fields – and the screen says *"The model moves to {target} when the test works."*
4. The user clicks **Test and save**. If the new name is already in the list of the provider the model will be on, the screen says *"That model is already in the list."* and nothing is tested or saved.
5. The system sends one short request with the typed values (or the target provider's saved key or address). **Nothing is saved before this test works.**
6. If the test fails, the reason is shown with "Nothing was saved.", the key box is emptied, the typed name is kept, and a model being moved stays where it was.
7. If the test works, the system renames the model and saves the key or address; when the provider was changed it moves the model to that provider (creating it first when it is new) and removes a custom provider the model left with no models. The model TFA uses does not change. The toast *"{model} was updated"* is shown and the user is returned to TFA Settings.
8. **Remove the key**: the system asks *"Remove the {Provider} key?"* ("The key is removed for every {Provider} model.", and, if TFA uses that provider, "TFA uses {Provider}, so TFA is unavailable until a key is added again."). After confirming, the key is removed without a test, the toast *"The {Provider} key was removed"* is shown, and every row of that provider shows "No key saved".

```mermaid
  B -- Yes --> C["Message: switch TFA first, OK"]
  B -- No --> D["Edit AI model: change name, key, address or provider"]
```

**Example:** `gemini-2.0-flash` (added, not in use) is edited, the provider is changed to the existing custom provider "OpenRouter" and the name to `google/gemini-2.0-flash-001`. The screen says "The model moves to OpenRouter when the test works." After a passing test the model is listed under OpenRouter and no longer under Google Gemini.

### 5.11 Step-by-Step Workflow – Add a Custom Provider
1. On TFA Settings, the user clicks **Add AI model**.
2. The user types a provider name that is not in the suggestions, for example "Groq". The **New provider** tag and the fields **API type**, **Runs**, **Server address** and **API key** (optional) appear.
3. The user chooses **OpenAI-compatible**, leaves **Runs** on **Cloud**, types `https://api.groq.com/openai/v1`, the model `llama-3.3-70b-versatile` and the Groq key. (A local server such as LM Studio – OpenAI-compatible, `http://localhost:1234/v1`, **Local** – needs no key.)
4. The user clicks **Test connection**. The screen checks the name (2 to 40 characters), the address (required, http or https) and the model name first, and sends nothing if one is wrong.
5. The system sends one short request to the typed address. **Nothing is saved before this test works.**
6. If the test fails, no provider and no model are created; the reason (naming the provider, for example "Groq did not accept the API key. …") is shown with "Nothing was saved." and the key box is emptied.
7. If the test works, the system creates the custom provider, adds the model, saves the key encrypted, switches it on and the other providers off. The toast *"{model} on Groq is now in use"* is shown, and TFA Settings lists a Groq group (Cloud, key ending shown) after the built-in providers, with that model **In use**. The TFA window now offers Groq and, because it runs in the cloud, shows the cloud notice for it.

| Permission Key | Description | Administrator | Manager | Employee | Custom Role |
|----------------|-------------|:-------------:|:-------:|:--------:|:-----------:|

> Manager and Employee values are the defaults given when the permission is first created. The Administrator role is given every permission again each time the application starts.

## 7. Related Modules
- **TaskFlow Assistant (TFA)** – Uses the model marked **In use** here, on a built-in or custom provider. Only configured providers are offered in the TFA window; a custom provider marked Cloud gets the same cloud notice as Gemini and OpenAI. TFA answers questions about TaskFlow from the project documents; that document search runs by itself in the background (on the built-in Ollama provider) and has no settings on this screen.
- **08.3 Role Configuration** – Grants the four `settings.ai.*` keys to custom roles.

## 8. Expected Outcome
The Administrator sees every model in one list, switches TFA to one with a single click, tests any of them, adds custom providers by name, and adds, edits, moves or deletes the models an administrator added, storing API keys safely without exposing them to anyone. Users of TFA are offered only the configured model.
